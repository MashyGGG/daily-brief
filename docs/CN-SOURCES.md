# 接入掘金 / 微信公众号 / 36氪

这三个源常被一起提，但它们的难度**差三个数量级**。这份文档记录实测结论和可选方案，
免得下次又从「找找有没有 RSS」重新开始。

所有探测结果的时间戳：**2026-08-20**，从一台中国大陆的机器发起。
runner 侧的可达性是另一回事，见 §4。

---

## 0. 结论速查

| 源         | 官方 RSS       | 代价                  | 现状            |
| ---------- | -------------- | --------------------- | --------------- |
| 掘金       | **有**         | 零                    | 已接入          |
| 36氪       | 死了           | 零代码 / 80 行 / 自建 | 方案 A 试运行中 |
| 微信公众号 | 没有，也不会有 | 高，且持续维护        | 建议放弃，见 §3 |

## 1. 掘金 —— 已接入

`https://juejin.cn/rss` 是活的官方 RSS 2.0，结构完整：CDATA 标题、真实的 per-item
`pubDate`、`description`、`dc:creator`。现有的 rss adapter 直接吃，零代码。

### 两个必须知道的限制

**分类参数是假的。** `?cate=frontend`、`?category=frontend`、`?sort=hot` 都返回 200，
看上去像是生效了。实测并发抓取对比文章链接集合：

```
默认 vs frontend   重合 90%
默认 vs backend    重合 90%
frontend vs backend 重合 100%   ← 两个不同分类，内容完全一样
默认 vs 乱写的分类  重合 90%     ← 参数根本没被读
```

那 10% 的差异只是抓取瞬间 feed 又更新了。**只有一个全站流**，没法按分类过滤。
所以给了低 weight（0.7），让它在「中文技术」栏里跟高信噪比的源公平竞争。
真要挑前端内容，用 section 的 `include` 关键词，不要指望 URL 参数。

**feed 窗口只有约 4 小时。** 20 条覆盖的时间跨度实测是 `02:34Z → 06:22Z`。
掘金发文密度太高，每天 08:00 跑一次，只能看到那一小段时间的文章。
这是掘金自身的限制，不是配置问题 —— 想要全覆盖只能提高抓取频率，
但那跟「每日早报」的产品形态冲突，不值得。

## 2. 36氪 —— 三条路，选一条

官方 `https://36kr.com/feed` 和 `/feed-newsflash` 现在返回的是 **SPA 的 HTML 壳**
（17KB，`<!DOCTYPE html>` 开头），不是 XML。历史上有过 RSS，早停了。

### 方案 A：第三方 RSSHub 镜像 —— **当前采用，试运行中**

```yaml
- name: 36kr-ai
  type: rss
  weight: 0.9
  params: { url: https://rss.injahow.cn/36kr/motif/327686782977 }
```

#### 先别用 `/newsflashes`

最先想到的 `/36kr/newsflashes` 能用，但**内容不对口**。实测 20 条标题：

> 2026年APEC海关与商界对话会在大连举行 · 三大股指集体翻绿 ·
> 今年前 7 个月香港 ETF 市场日均成交额 406 亿 · 神龙汽车科技（武汉）有限公司正式成立

这是**财经通稿线**，不是科技内容。而且 20 条只覆盖 **1.5 小时** ——
36氪 快讯发布密度极高，日更一次基本只能看到出报前那一小段。

#### 用 `/motif/327686782977`（「人工智能·AI」专题）

同一个镜像上换个路由，内容完全不同：

> 王兴兴进入奥德赛时期 · Sora 退场，国产崛起：AI 视频生成的"拐点"时刻 ·
> AlphaFold 刚解散，Claude 进军蛋白质设计 · DeepSeek Harness 首发新版本 ·
> 中国掐住了 CPO 的七寸

深度报道，且时间跨度 **16.7 小时**，基本覆盖得住日更窗口。
标题有 36氪 一贯的标题党味道（"神话破灭？""OpenAI 要输？"），所以 weight 压到 0.9。

#### 这个镜像上哪些路由是活的

只有两个。其余全部 503：

| 路由                  | 结果                 |
| --------------------- | -------------------- |
| `/36kr/newsflashes`   | 200，20 条，财经快讯 |
| `/36kr/motif/:id`     | 200，20 条，按专题   |
| `/36kr/news/latest`   | 503                  |
| `/36kr/news/ai`       | 503                  |
| `/36kr/hot-list/:cat` | 503                  |
| `/36kr/user/:id`      | 503                  |

`motif` 的 id 可以从 36氪 网页 URL 里抄：`https://www.36kr.com/motif/<id>`。

#### 这个方案的代价，说清楚

- 这是**别人的服务器**，随时可能关停、限流或改变行为
- 你的抓取行为对该实例运营者可见
- 官方 `rsshub.app` 已被 Cloudflare 挡住（403 "Just a moment..."），
  `rsshub.rssforever.com` 返回 503 —— 公共镜像的死亡率就是这么高
- 一旦挂掉，只会在早报里留一条抓取告警（A5 失败隔离），不影响其它源出报

试运行期间「中文技术」栏的 `limit` 从 4 提到了 5，好让新源有机会露面被评估。
**决定不留就把 limit 调回 4，并删掉这个源。**

### 方案 B：自己写一个 36kr source adapter（约 80 行）

36氪 的内部 API 可用，我把参数试出来了：

```
POST https://gateway.36kr.com/api/mis/nav/newsflash/flow
Content-Type: application/json

{"partner_id":"wap","param":{"siteId":1,"platformId":2,"pageSize":20,"pageEvent":0},"timestamp":<ms>}
```

`pageEvent` 是必填的，且**必须是 `0`**：

| 参数                           | 响应                              |
| ------------------------------ | --------------------------------- |
| 不带 `pageEvent`               | `code:1 "分页动作不能为空"`       |
| `pageEvent:1`                  | `code:1 "请求分页回调值不能为空"` |
| `pageEvent:1, pageCallback:""` | `code:1 "请求分页回调值不能为空"` |
| **`pageEvent:0`**              | **`code:0`，20 条快讯**           |

接入方式跟 `hackernews` / `github` 一样：在 `src/sources/` 加一个 fetcher，
在 `FETCHERS` 注册一行，在 `sourceSchema` 加一个 discriminated-union 分支。
`src/sources/hackernews.ts` 是最接近的范本（同样是 JSON API + 自定义 parser）。

代价：这是**未公开的私有 API**，字段名和鉴权随时可能变，坏了只能重新逆向。
好处是没有第三方依赖，且失败会走 A5 的隔离逻辑，只留一条告警。

### 方案 C：自建 RSSHub

最稳，也最重 —— 要养一个常驻服务（Docker / Vercel / Cloudflare Workers），
而且它必须能被 GitHub Actions 的 runner 访问到，也就是得有公网地址。
一旦建起来，掘金分类、36氪、知乎、B站等等都能一起解决。

适合：将来想接的中文源超过 3 个的时候。为了 36氪 一个源建这个不划算。

## 3. 微信公众号 —— 建议放弃

这是三者里唯一**没有干净解法**的。

### 为什么没有官方路

微信公众平台的 API 只能读**你自己的**公众号素材。想订阅别人的号，官方从未开放过接口，
这是产品策略，不是技术缺失。所有第三方方案本质上都是在绕这一点。

### 生态现状（实测）

- **wewe-rss**（9.6k ★，曾经的主流自建方案）—— **已 archived**，最后提交 2026-03-20
- GitHub 上搜 `wechat rss` 按更新时间排，前 12 个全是 0～3 star 的个人仓库
- RSSHub 的 `/wechat/*` 路由在公共镜像上返回 503（这类路由依赖搜狗微信等中间源，
  反爬极严，公共实例基本都关掉了）
- `feeddd.org` 域名已解析失败

也就是说：**曾经能用的方案正在集体死亡**，剩下的要么是付费服务，
要么是需要你挂一个微信号/微信读书账号常驻的自建方案。

### 如果一定要接

现实里只剩两条：

1. **付费托管服务**（如 wechat2rss 一类）—— 花钱买 RSS 地址，然后当普通 rss 源接。
   零代码，但引入了持续订阅成本和一个第三方依赖。
2. **自建 + 挂账号** —— 需要一个常驻的微信读书 / 微信账号做数据源，
   有封号风险，且要跟着微信的反爬策略持续维护。

### 更划算的替代

公众号里真正有技术价值的内容，绝大多数会同步或被转载到已经接入的源：

- 大厂技术号 → `meituan-tech`、`infoq-cn`、`juejin`
- 行业分析 → `infoq-cn`、`oschina`
- 个人技术号 → 作者通常同时在掘金 / 个人博客发

投入产出比很低。**除非有某个特定的号是你非看不可且只在微信发**，
否则这一项建议直接跳过。

## 4. 一个所有方案共同的前提：runner 在美国

**本文所有探测都是从中国大陆的机器发出的，这不能证明 GitHub Actions 能抓到。**
`ubuntu-latest` 的 runner 在美国，中国站点从境外 IP 的可达性是独立的一件事 ——
可能慢、可能被 CDN 区别对待、也可能完全正常。

验证成本很低，别靠猜：

```bash
# 在仓库的 Actions 页面手动触发，勾上 dry-run
gh workflow run daily-brief.yml -f dry-run=true -f sections=cn-tech
```

然后看输出里的**抓取告警**段落 —— 单源失败只会留一条 warning
（A5 的失败隔离），不会影响其它源。哪个源在 runner 上抓不到，一眼就能看出来。

如果某个中文源在 runner 上确实不可达，可选：

- 把它换成方案 A 那种境外可达的镜像
- 或者接受它长期告警（不影响出报），等哪天换方案
