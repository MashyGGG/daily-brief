# AI 短剧／漫剧：从了解、练习到制作与发布的执行手册

更新：2026-10-30。适用对象：准备从零进入 AI 漫剧／短剧，希望兼顾创作和后续技术开发的个人。

## 1. 目标、默认选择与使用方式

目标是建立能反复执行的闭环：看懂案例 → 小练习 → 完整样片 → 小范围发布 → 数据复盘 → 技术改进。日报负责持续发现变化和提醒行动；这份手册负责稳定的操作步骤。不要等“了解完所有工具”再开始。

建议从 **30–60 秒、单角色、单场景、旁白驱动的动态漫** 起步，再做双角色对话，最后尝试写实短剧与系列化。先用参考图和有限运动降低角色漂移、复杂动作及口型同步的难度。这是针对你的目标给出的执行建议，不是行业统一标准。

- 初始阶段：`observe`，不按日期自动升级。
- 建议每日 30–60 分钟；每周另留一次 1–2 小时制作时间。时间不足时延长阶段。
- 先做一部原创小作品；风格、工具、平台各固定一个主选项。
- 预算先由自己填写：学习期月上限 ____ 元，首个样片上限 ____ 元。记录积分实际消耗，不把失败生成当作免费。
- 当前假设：使用现有邮件收件人与抄送、北京时间每天 08:10 启动日报。硬件、预算和目标平台尚未确认，本手册不预设你有显卡或必须买会员。

## 3. 学习期间每天做什么

收到邮件后依次做以下动作，最多收藏 3 条、精读 1 条：

1. 用 5 分钟扫国内外变化：只找与当前作品或阶段有关的更新。
2. 用 10–15 分钟读一篇完整教程或官方说明；区分作者演示、厂商宣传和自己实测。
3. 用 15–30 分钟做一个动作：写一个分镜、生成一张参考图、重做一个镜头或修一段字幕。
4. 用 5 分钟记录：今天完成什么、失败在哪里、下次只验证什么。
5. 高阶论文和大型部署先记入“以后再看”，每周最多安排一次技术专题阅读。

建立三个列表：`本周要试`（最多 3 项）、`资料库`、`暂不做`。每周清理没有明确用途的收藏。

## 4. 阶段与升级条件

| 阶段配置   | 重点                     | 升级条件                                                   |
| ---------- | ------------------------ | ---------------------------------------------------------- |
| `observe`  | 概念、案例、最小练习     | 能说清制作链路，有 3 份案例拆解和 1 个 5–10 秒练习         |
| `practice` | 角色稳定、单镜头、剪辑   | 同一角色的 3 个镜头可拼接，能重复完成一个镜头              |
| `pilot`    | 完整叙事                 | 完成 30–60 秒样片；至少 2 位未看脚本的人能复述故事         |
| `publish`  | 小规模发布与反馈         | 发布并完成两轮记录和修改；确认自己能承受制作成本           |
| `engineer` | 开源复现、工作流与自动化 | 同一镜头可复现，成本和成功率有记录，完成一个稳定自动化环节 |

技术阅读可以贯穿全程；`engineer` 表示当前行动重点，不表示发布后才允许学技术。可回退到上一阶段。阶段由你在 `brief.config.yaml` 的 `aiDrama.stage` 手动修改并提交，系统不会根据阅读量、天数或邮件打开率推断进度。

## 5. 开始制作：第一部动态漫的标准流程

### 5.1 立项（开始前完成）

- 只选一个受众、一个情绪、一个冲突、一个结尾。
- 限定单角色、单主要场景，6–10 镜头，30–60 秒；这是练习约束，可按实际简化。
- 示例题材：主人公找到一封写给明天自己的信，结尾发现信是今天写的。自行写原创情节，不照搬现有作品。
- 确定画幅：首发平台偏竖屏就先按 9:16 制作；首部只交付一个画幅。
- 选一个图像工具、一个视频工具、一个剪辑工具，使用自己的合法账户。

### 5.2 先做故事和声音

1. 写一句话梗概，然后扩展成三段：吸引注意 → 发生变化 → 收束或悬念。
2. 读出旁白并计时，根据实际语速缩短文字；不要靠估算字数硬凑时长。
3. 生成或录制临时旁白，先确认情绪与节奏。
4. 把每个叙事动作分到分镜表里；每镜头先安排一个主要动作。

分镜表模板（复制到个人制作项目填写）：

| 编号 | 目的／画面   | 景别／镜头运动 | 时长 | 台词／声音 | 角色与场景参考  | 提示词／模型版本 | 状态 |
| ---- | ------------ | -------------- | ---- | ---------- | --------------- | ---------------- | ---- |
| S01  | 开头建立问题 | 中景，固定机位 | 5 秒 | 临时旁白   | char-A / room-A | 待填             | 待做 |

### 5.3 建立角色和风格资料

1. 固定脸型、发型、服装、色彩和画风，生成正面、侧面与必要表情参考。
2. 固定场景布局、时间、光线；将参考图命名，不靠聊天历史找图。
3. 先生成关键分镜静帧，检查角色是否相同，再尝试运动。
4. 先用临时图做粗剪：故事看不懂时改分镜，不继续堆精细画面。

图像提示词模板：`角色固定描述＋当前表情和姿态＋场景＋景别构图＋光线＋统一画风`。

视频提示词模板：`引用参考图＋一个主要动作＋镜头运动＋运动幅度＋保持不变的角色和场景特征`。

模型不支持的参数不要强行照搬；种子、参考强度等只在产品实际提供时记录。

### 5.4 逐镜生成与质检

1. 先试最难镜头；失败就改为特写、旁白或切镜表达，不必用复杂动作硬撑。
2. 每镜最多连续尝试 3 次后停下来诊断：输入图、动作、构图、时长还是模型限制？这是预算纪律，不是模型能力保证。
3. 每次只改一个变量，保留成功版本与参数。
4. 检查脸、服装、肢体、道具、背景跳变和运动连续性；不合格片段不进入最终剪辑。
5. 旁白型动态漫可以先不做口型；对话型作品再单独加入声音与口型测试。

### 5.5 剪辑和成片验收

1. 按分镜放入时间线，先完成能看懂的粗剪，再优化节奏。
2. 添加最终旁白、必要音效、授权音乐和字幕；校对人名、断句、字幕安全区和音量。
3. 输出预览，在手机上全程观看一次，检查黑帧、截断、文字遮挡和声音突变。
4. 请 2 人盲看：故事讲了什么？哪个位置看不懂？是否愿意看下一条？
5. 只修最影响理解的 3 个问题，再决定是否公开。

项目目录建议（放在自己的制作素材目录，默认不要把大量视频或私人素材提交到本仓库）：

```text
project-001/
  01-script/       梗概、台词、分镜
  02-reference/    角色、场景、风格参考及来源
  03-shots/S01/   图片、视频、提示词、参数和版本
  04-audio/       配音、音乐、音效及授权记录
  05-edit/        剪辑工程
  06-export/      预览与最终版本
  log.md          工时、费用、失败原因、复盘
```

## 6. 发布：先完成一次小闭环

第一部先在自己常用、愿意持续运营的一个平台做普通作品试发。可先私密预览，再公开。平台选择取决于受众、作品形态和账户可用功能，不能仅凭“哪个平台变现快”的教程决定。

发布前逐项完成：

- [ ] 保存剧本、图片、音乐、音色、字体及模型的授权或许可证依据；开源代码许可不等于所有模型、素材和输出均可商用。
- [ ] 检查是否使用他人肖像、声音、商标或 IP；需要授权的素材先解决授权。
- [ ] 打开目标平台当日的发布规范与 AI 内容声明入口，记录核查日期。
- [ ] 按要求声明 AI 生成，保留生成工具提供的必要标识。
- [ ] 标题、封面和简介准确表达故事，不虚构收益、真人事件或合作关系。
- [ ] 手机检查清晰度、字幕、音量、封面裁剪与播放完整性。
- [ ] 保存发布链接、时间、版本和平台审核结果。

依据：[国家网信办标识办法](https://www.cac.gov.cn/2025-03/14/c_1743654684782215.htm)规定了生成合成内容标识要求；[抖音官方治理公告](https://trust.douyin.com/article/15868)说明了主动声明与平台标识。具体发布入口和平台规则在操作当天重新核查。本手册不将旧截图中的菜单位置视为长期不变。

普通短视频试发与正式微短剧发行、备案、平台商业合作属于不同操作范围。若计划商业微短剧、付费分发或参加平台项目，先核查届时主管部门及平台的适用要求，再按其流程推进；本手册不替代准入与发行审核。

发布后 24 小时、72 小时各记一次可获得的数据：曝光、播放、平均观看时长、完播、互动、观众评论。不同平台口径分开记录，样本太小不做收益推断。

- 开头流失：检查前几秒是否交代问题，下一版只改开头。
- 中段流失：检查信息重复、镜头过长或因果不清。
- 评论说看不懂：先改叙事，不先升级模型。
- 制作成本过高：减少复杂镜头并复用角色和场景。

首轮目标是验证“能持续制作和改进”，不设必须爆款或赚钱的承诺。完成 2–3 部小作品后，再决定是否系列化。

## 7. 技术方面如何逐级进入

| 层级   | 学习问题                                                 | 实践验收                                             |
| ------ | -------------------------------------------------------- | ---------------------------------------------------- |
| 基础   | 图生图、图生视频、参考图、种子、分辨率、帧率分别影响什么 | 用同一镜头只改一个参数并比较                         |
| 工作流 | 模型、节点、插件、依赖和输入输出如何连接                 | 复现官方 ComfyUI 图片样例，再复现视频样例            |
| 部署   | 模型版本、显存、内存、磁盘、推理速度、许可证             | 按官方要求核对现有设备；无合适显卡先评估短时云 GPU   |
| 可复现 | 参数、模型文件版本、工作流和素材能否还原                 | 保存工作流 JSON、模型标识、节点版本及运行记录        |
| 开发   | 哪一步已经稳定、重复且值得自动化                         | 先做分镜清单、文件命名或字幕整理，再尝试生成任务排队 |

第一次技术实验仍用首作的同一镜头：固定参考图和时长，比较云端产品与开源路线的可用率、人工修正时间、费用、等待时间。不要只比一张最好的展示图，也不要套用厂商没有说明条件的显存数字。

后续开发顺序建议：素材台账 → 分镜／任务状态 → 提示词与版本管理 → 批量生成和重试 → 质检与剪辑辅助。发布先人工确认。本日报项目负责发现和学习提醒，制作工具应单独立项，避免把视频生成和大文件塞进邮件流水线。

## 8. 本项目已经落地的功能

本地代码与配置已完成以下能力；上线仍需部署及真实邮件验证：

- 独立 `ai-drama` 期次，北京时间 08:10 启动，资讯与技术回溯 48 小时，教程回溯 30 天，只发 `me-mail`。
- 资讯与案例最多 10 条、教程与制作方法最多 6 条、工具模型与开源更新最多 10 条。
- 6 组中英文专题 Google News RSS（资讯、教程、工具模型），以及 ComfyUI、LTX-2 Releases；旧 HunyuanVideo Release 源暂不参与自动采集。
- 直接订阅 Comfy 官方博客和 Hugging Face 官方博客；只挑选与制作相关的教程或技术内容，不把整站新闻都当教程。
- 专题独立历史去重组及增量来源状态文件，避免与原有早晚报互相消耗内容；教程历史去重同步覆盖 30 天。
- 先判断主题相关性，再把教程优先归入教程栏；同一篇内容优先保留原作者来源，最终仍按资讯、教程、技术的顺序展示。
- 按当前阶段给相关关键词加权（最多加权 45%），保留原来的新鲜度、来源配额和其他重要动态。
- 生成摘要时传入当前阶段，提取适用环节、难度、前置条件、最多 5 个步骤及限制；原文未说明则不填。
- 制作笔记明确标识“已提取正文”或“仅来源摘要”，不将厂商示例当成本项目实测。
- 专题每封邮件的最后显示五步路线、当前阶段、小练习、完成标准及本手册链接；HTML、纯文本和 Markdown 归档均支持。
- 每阶段两份固定教材按日期轮换，明确标为常青教材，学习阶段不会自动升级。
- 提醒、教材、制作笔记写入归档；重发保留当时快照。
- 无新增内容也发送学习提醒；来源失败与 AI 整理未启用时分别提示。
- 专题独立输出 token 配置与摘要条数上限，同时保留全局输入预算约束。
- 自动触发会读取发送记录，已确认成功的收件人跳过；未成功的收件人从原归档重试，不重新采集与生成摘要。

### 邮件与发送记录

收件人沿用 `EMAIL_TO` / `EMAIL_CC`，不需要新邮箱或第二套 SMTP。邮件主题为 `AI短剧·漫剧日报 · 日期`，不作为回复邮件发送。后续若增加不同收件人，需调整目前全局 EMAIL_TO 覆盖所有邮件收件人的实现。

投递结果保存在 `archive/delivery/YYYY-MM-DD.ai-drama.json`，只有收件人配置 ID、状态与时间，没有邮箱地址、错误原文或邮件正文。自动运行以归档保存内容、以投递记录判断是否还需发送；原有早晚报保留原来的行为。

自动触发包括 cron 和 `--skip-if-archived`；人工直接运行或明确 `--from-archive` 仍可主动重发。记录损坏时停止并报错，避免把损坏当成“未发过”。文件写入和远端归档提交之间仍有窗口：SMTP 已接受但记录未保存／未提交时，无法保证绝对只送一次。修复这类情况先检查运行日志和邮箱，再决定人工重发。

### 配置与实际限制

```yaml
aiDrama:
  stage: observe
  maxSummariesPerRun: 26
  summaryMaxOutputTokens: 800
```

摘要条数同时受 `llm.budget.maxItemsPerRun` 限制，实际取较小值；输入字符预算与模型并发／超时继续受原项目配置约束。缺少 LLM_API_KEY 或关闭模型时，邮件保留原始标题和来源摘要，仍包含固定教材与练习。

Google News 不等于整个互联网，可能漏掉 B 站、公众号、YouTube 和平台内部内容；聚合链接的正文提取也可能失败。同一新闻在不同语言下的转述仍可能残留重复。新闻／教程 Feed 有交集，去重后某栏不足其条数上限是正常现象；30 天教程不等于今日发布的资讯。

手册链接指向仓库 main 分支；部署前该链接不会包含本次新增文档。仓库改名或换默认分支时需要同步链接策略。常青教材不是每日重新审核的新闻，首次使用时核对当前工具版本；其小练习可以在你现有的工具中完成。

来源入口、实现结构与验证方法见 [IMPLEMENTATION.md](IMPLEMENTATION.md)。

## 9. 可选增强（不作为首次使用的前置条件）

1. 增加经过人工验证的创作者订阅和官方教程更新源，逐个确认合法公开入口与解析方式。
2. 接入可配置的搜索 API，扩展聚合 RSS 没有覆盖的内容；需单独配置供应商、凭证和费用预算。
3. 增加代码／模型／工作流的结构化链接与原文证据定位；当前统一使用条目的原始链接，模型不会自由生成下载地址。
4. 对没有 Releases 的项目监测 README 或文档版本差异，维护明确事件身份，不把旧仓库首页当作新资讯。
5. 增加发送状态的远端持久化与更细的失败恢复，缩小 SMTP 成功到 git 提交之间的状态丢失窗口。

## 10. 上线、操作和验收

### 开发／维护命令

```sh
pnpm validate
pnpm brief:schedule
pnpm check:schedule
pnpm typecheck
pnpm test
pnpm brief:ai-drama:preview
```

若本机 pnpm 的依赖状态检查阻止命令启动，可直接运行已安装的入口检查，避免为了运行检查而随意批准未知安装脚本：

```sh
node node_modules/tsx/dist/cli.mjs src/index.ts --validate-only
node node_modules/tsx/dist/cli.mjs src/schedule/generate.ts --check
node node_modules/typescript/bin/tsc --noEmit
node node_modules/vitest/vitest.mjs run
node node_modules/tsx/dist/cli.mjs src/index.ts --schedule ai-drama --dry-run --no-llm
```

### 部署步骤

1. 审阅并提交本次代码、配置、生成的 workflow 和本手册到 main。
2. 检查已有 SMTP、EMAIL_TO、EMAIL_CC 配置；需要中文 AI 摘要时检查 LLM_API_KEY，原项目变量设置继续有效。
3. GitHub Actions 手动运行 `ai-drama`，先勾选 dry-run，确认来源、独立主题、正文和末尾五步提醒。
4. 再执行一次真实运行，确认 Summary 中邮件为 sent，并在邮箱检查收件人、正文、手册链接与垃圾箱。
5. 若使用外部定时器，增加北京时间 08:10 调用，cron 输入为 `10 0 * * *`；内置 GitHub cron 作兜底。没有外部定时器时也能运行，但可能延迟。
6. 两类定时触发均进入专题发送恢复逻辑：成功收件人跳过，失败收件人使用已归档内容重试。检查记录是否已随 workflow 提交到 main；未完成状态提交的异常见第 8 节。
7. 首周观察送达时刻、来源失败、重复与无关条目；根据实际结果调整关键词和来源，而不是扩大到所有 AI 新闻。

采集、模型和排队都需要时间，08:10 表示启动时间，不是精确送达承诺。整个 workflow 当前为串行排队、10 分钟运行上限，新增来源或摘要负载后应看实际耗时再调。

### 日常操作

- 阶段切换：修改 `aiDrama.stage` 并提交；阶段不变时邮件持续提醒同一目标。
- 修改时间：修改 `schedules` 的 `ai-drama.time`，运行 `pnpm brief:schedule`；若有外部定时器也同步修改。
- 自动补发：同一天以原 cron 触发；只重试未确认成功的收件人。强制人工重发：Actions 指定 `ai-drama` 和 from-archive 日期，或直接使用人工 schedule 入口。先确认历史结果。
- 暂停专题：将该期次 `enabled` 设为 false，重新生成 cron，并暂停相应外部定时器。
- 平台发布动作由你完成，本项目不会替你开通账号、购买工具、上传作品或自动发布。

### 验收清单

- [ ] 新邮件独立主题，只走邮件；原有早晚报、新闻、周报栏目不混入专题。
- [ ] HTML 和纯文本最后均有五步路线、当前阶段及可访问手册链接。
- [ ] 改变阶段后新邮件提醒变化，归档重发仍显示当时快照。
- [ ] 零条目仍提醒，来源失败与正常无更新可区分。
- [ ] 同专题历史去重，专题与技术早报互不吞内容。
- [ ] 摘要缺凭证、正文提取失败时仍有可追溯链接和来源摘要。
- [ ] 真实邮件送达、定时运行、归档提交分别核查，不能仅看绿色勾号。

## 11. 个人复盘模板

```text
本周阶段：

实际可用学习／制作时间：
精读的 1–3 份资料及链接：
完成的产物（文件／视频）：
最大的一个问题：
下周只验证的问题：
工具与模型版本：
尝试次数／可用镜头数／人工返工时间：
费用与积分消耗：
发布链接及 24/72 小时数据（如有）：
是否达到本阶段升级条件：
```

今天就可以做：选一条喜欢的 30–60 秒作品，拆成镜头表；选一个原创点子；生成一张角色参考图。本周的最小成果是一条 5–10 秒练习，不是更多收藏。
